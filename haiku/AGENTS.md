# Notes for agents and contributors - Haiku port

Engineering notes for changing this code. The README is build-and-run only;
everything about *why the code looks like this* lives here.

Written in English to match the source comments.

## What this is

A Haiku Wi-Fi analyzer in C++ against the native API: it scans for access points
and draws them as bell curves over a channel axis, one graph per band. Same graph
as the [Windows Phone port](../winphone), which came first and whose layout
constants and colour palette this port inherits.

## Module map

```
Makefile                  driven by the system makefile-engine
RWiFiAnalyzer.rdef        signature, version, bitmap icons
icons/*.raw               B_CMAP8 icon data, generated by tools/make-icon.py
tools/make-icon.py        draws the icons; needs Pillow, runs off-Haiku too
src/App.cpp               BApplication; opens the window in ReadyToRun
src/MainWindow.cpp        controls, the 5 s BMessageRunner tick, status line
src/SignalGraph.cpp       all the drawing - axes, grid, curves, labels
src/WifiScanner.cpp       scan trigger + scan result parsing
src/net80211.h            the private kernel interface, copied in. Read this first
src/ChannelMap.cpp        frequency <-> channel number arithmetic
src/AccessPoint.h         one BSS from a scan
```

## The one real problem: the public API throws the channel away

`BNetworkDevice::GetNetworks()` returns `wireless_network` records, and
`wireless_network` has **no frequency or channel field** - only name, address,
signal strength, noise, and the security parameters. A channel graph cannot be
drawn from it.

The records are built from `ieee80211req_scan_result`, which *does* carry
`isr_freq`; Haiku's `fill_wireless_network()` simply does not copy it across. So
this app skips the Kit and issues the same ioctl itself:

```
socket(AF_INET, SOCK_DGRAM, 0)
ioctl(fd, SIOCG80211, &ieee80211req{ .i_type = IEEE80211_IOC_SCAN_RESULTS })
```

`src/net80211.h` is the smallest copy of that interface that works. Those
definitions live in `src/libs/compat/freebsd_wlan/net80211/ieee80211_ioctl.h` in
the Haiku *source tree*, not in the installed development headers, so they cannot
be included - only reproduced. Three details are load-bearing:

1. **`i_name` is 32 bytes, not 16.** The kernel's copy of `ieee80211req` resolves
   `IFNAMSIZ` through Haiku's `<net/if.h>`, where `IF_NAMESIZE` is 32. FreeBSD's
   own header says 16. Get this wrong and every field after the name is off by 16
   bytes.
2. **`SIOCG80211` is `SIOCEND + 235`.** Haiku's FreeBSD compatibility layer defines
   `_IOWR(g, n, t)` as `SIOCEND + n`, and `SIOCEND` is 9000 in `<sys/sockio.h>`.
   The FreeBSD encoding of `_IOWR` would produce a completely different number.
3. **`isr_rssi` is in half-dBm above the noise floor**, per net80211's own comment,
   so dBm is `isr_noise + isr_rssi / 2`. Reading it as dBm directly puts every
   curve near the top of the graph.

`ReadNetworks()` sanity-checks `isr_len` and `isr_ie_off` against
`sizeof(ieee80211req_scan_result)` on every record and stops with *"Scan result
layout mismatch"* if either is short. The kernel sets `isr_ie_off` to its own
`sizeof`, so a mismatch is exactly the signal that this header has drifted from the
kernel's - and stopping beats walking off the end of the buffer or drawing garbage.
If that message ever appears, diff `src/net80211.h` against the current
`ieee80211_ioctl.h`.

The SSID is read from `isr_ie_off`, not from `result + 1`. Both are the same
address today, but only the first is what the kernel promises.

## Channel width comes from the beacon, not from the scan result

`isr_flags` looks like the answer and is not. It is a `uint16` copy of net80211's
`ic_flags`, and every HT flag - `IEEE80211_CHAN_HT20`, `HT40U`, `HT40D` - sits at
bit 16 or above, so all of them are truncated away before the struct is filled.

What does survive is the beacon's own elements: `isr_ie_len` bytes of them, sitting
after the SSID and mesh ID. `_ChannelGeometry()` in `WifiScanner.cpp` walks them for
HT Operation (61) and VHT Operation (192), which give both the width and the centre
of the occupied channel. The centre matters as much as the width - a 40 MHz BSS puts
its extension channel on one side of the primary, so a 42 MHz curve centred on the
primary would claim 20 MHz of spectrum that is in fact free.

Verified against a live scan: 40 MHz neighbours come out 42 MHz wide and offset by
10 MHz, in both directions, exactly where the neighbouring 20 MHz networks say they
should be.

## Scanning without blocking the window

`BNetworkDevice::Scan(wait, forceRescan)` with `wait = true` returns when the
scan-finished notification arrives - a second or two later. Called from
`MessageReceived` that freezes the window on every tick.

So each tick does it in this order:

1. read the results the *previous* tick asked for,
2. redraw,
3. trigger the next scan and return immediately.

The consequence is that results are always one tick old, which for a 5 s tick is
what any of these apps show anyway - and it means no threads, no locking, and no
`BMessageRunner` tick ever waiting on the radio. It also means a cold start needs
two ticks before the graph fills in; the README says so.

`forceRescan = false` deliberately leaves the driver's cache alone, so a scan
refused because one is already running costs nothing.

## Drawing decisions

Inherited from the phone port unless noted:

- **A plain `BView` with `Draw()`, no offscreen bitmap.** The whole plot is rebuilt
  per scan; at a few dozen networks that is a few hundred primitives and the
  app_server composites one update session, so there is nothing to double-buffer
  around. If flicker ever shows up on slow hardware, that is the thing to add.
- **`FillPolygon`/`StrokePolygon`, not `BShape`.** The bells are two mirrored cubic
  segments - control points at 0.6 of the half-width, lower looks spiky, higher
  looks square - sampled into 12 points each. The first attempt built a `BShape`
  with `BezierTo` and `FillShape`/`StrokeShape` drew **nothing at all**: no error,
  no partial output, and the labels around it drawn correctly. Rather than chase it,
  the curve is sampled here. Twelve points per segment is past the point where the
  facets show at any window size this app is used at.
- **Translucent fills need the drawing mode changed.** `B_OP_ALPHA` with
  `SetBlendingMode(B_CONSTANT_ALPHA, B_ALPHA_OVERLAY)` is what makes the alpha in
  the high colour mean anything; the mode is set back to `B_OP_COPY` before the
  stroke and the text, which are opaque.
- **Every colour drawn in `B_OP_COPY` must be opaque.** `B_OP_COPY` ignores the
  alpha channel outright, so the grid's first spelling - white at `0x3c` alpha,
  copied from the phone port where the XAML brush honoured it - drew as *solid
  white* over the whole plot. It is a flat dark grey now. Anything translucent has
  to go through the `B_OP_ALPHA` path above.
- **`ConstrainClippingRegion` around the curves only.** A curve at the edge of the
  domain runs past the plot area. Labels are deliberately outside the clip, because
  they sit above the peak and the strongest ones would be cut off at the top.
- **The 2.4 GHz axis is fixed at 2400-2500 MHz**; the 5 GHz axis is fitted to the
  networks present and widened to a 200 MHz minimum.
- **Labels de-collide upward**, up to six steps, placed strongest-first so the
  strongest network keeps the spot it wants. Same as the macOS port, and for the
  same reason: a desktop window shows every network at once.
- **Colours come from an FNV-1a hash of the BSSID.** Any stable hash would do; the
  point is that it must not be seeded per process, or a network changes colour on
  every launch.
- **The plot is dark regardless of the system colours.** It is a chart, not a
  control, and the 12 curve colours were picked to separate from each other against
  black.

## The icon is a bitmap, not HVIF

Haiku icons are normally HVIF vector data in a `BEOS:ICON` attribute, produced by
Icon-O-Matic. There is no way to generate HVIF from a script, so the rdef instead
imports 32x32 and 16x16 `B_CMAP8` bitmaps into `BEOS:L:STD_ICON` and
`BEOS:M:STD_ICON`, which is what `BAppFileInfo::GetIconForType` falls back to when
there is no vector icon. `tools/make-icon.py` draws them from the same glyph the
other two ports use and quantises against Haiku's 8-bit system palette (index 255
is transparent; there is no alpha channel, so the anti-aliased edge becomes one
lighter green).

Replacing them with a proper vector icon is a strict improvement - open
`icons/icon-large.raw`'s source glyph in Icon-O-Matic, export the rdef snippet, and
swap the two `resource(101, ...)` lines for `resource vector_icon`.

## Deliberate omissions

- **No connect / disconnect.** `BNetworkDevice::JoinNetwork` exists; this is a
  measurement tool and joining networks is what the Network preferences are for.
- **No 6 GHz band.** Haiku's wireless drivers come from a FreeBSD import that
  predates 6E; there is no hardware here to draw.
- **No security-suite parsing.** Naming WPA2 versus WPA3 means reading the RSN
  element, and the elements are already walked for the channel width, so this is
  cheap to add if anyone wants it. Today the app reports the capability bit it is
  given: encrypted or open.

## The README screenshot

`docs/screenshot.png` is a real scan - real channels, real widths, real signal
strengths - with only the names replaced: `WifiScanner.cpp` was temporarily patched
to put `Network <n>` where the beacon's SSID goes, so nobody's network names are in
the picture. Beacons that carry no name still read `(hidden)`, because that is
information about the band rather than about a person.

If you retake it, do the same - patch, build, capture, revert - and use Haiku's own
`screenshot -s -w -b` to get the window on its own rather than cropping the desktop.

## Build on a 32-bit install: use the secondary architecture

On an `x86` Haiku, plain `gcc` is **2.95.3** - the x86_gcc2 compiler kept for BeOS
binary compatibility - and it cannot compile this: `std::vector`, `<algorithm>` and
C++11 are all past it. Build through the secondary architecture instead:

```
setarch x86 make
```

which is gcc 13 and produces `objects.x86-cc13-release/WifiAnalyzer`. On `x86_64`
there is no gcc2 and plain `make` is enough.

`LIBS` in the Makefile is assigned with `=`, not `:=`, on purpose:
makefile-engine defines `STDCPPLIBS` *after* the `include` line, so an immediate
assignment expands it to nothing and the link fails with undefined references to
`std::__throw_length_error` and friends - which reads like a broken toolchain and is
not.

## Verification status

- Built and run on Haiku R1~beta6 hrev99002, `x86` (32-bit), via `setarch x86 make`.
  Compiles with `WARNINGS := ALL` and produces neither errors nor warnings.
- Run against a live scan on an `atheroswifi` adapter: 32 networks found and drawn,
  names, channels, colours and the dBm axis all correct, and the 40 MHz networks
  drawn 42 MHz wide and offset to the correct side.
- The icon resources land as `BEOS:L:STD_ICON` (1024 bytes) and `BEOS:M:STD_ICON`
  (256 bytes) and Deskbar draws them, so the `rc` `import` path and the CMAP8
  quantisation both work.
- Installed at `~/config/non-packaged/apps/WifiAnalyzer`, with a Deskbar link in
  `~/config/settings/deskbar/menu/Applications`.
- **Not verified:** the 5 GHz graph, because the only adapter here is a 2.4 GHz-only
  802.11n radio, so nothing has ever appeared on that band. The VHT branch of
  `_ChannelGeometry` has therefore never run either. `x86_64` and `arm64` builds are
  untested for the same "no machine to hand" reason.
