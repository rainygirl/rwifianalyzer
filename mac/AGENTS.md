# Notes for agents and contributors - macOS port

Engineering notes for changing this code. The README is build-and-install only;
everything about *why the code looks like this* lives here.

Written in English to match the source comments.

## What this is

A macOS Wi-Fi analyzer in Swift/SwiftUI: it scans for access points and draws them
as bell curves over a channel axis, one graph per band. Same graph as the
[Windows Phone port](../winphone), which came first and whose layout constants and
colour palette this port inherits.

## Module map

```
Package.swift                  SwiftPM, macOS 14 minimum, Swift 5 language mode
Makefile                       assembles "R WiFi Analyzer.app" around the SwiftPM binary
Resources/Info.plist           bundle identity + NSLocationWhenInUseUsageDescription
Resources/AppIcon.icns         generated by tools/make-icon.py (needs Pillow)
Sources/WifiAnalyzer/
  App.swift                    @main, the Window scene, activation policy
  Models/AccessPoint.swift     one BSS from a scan
  Services/ChannelMap.swift    channel number <-> frequency, per band
  Services/WifiScanner.swift   CoreWLAN -> [AccessPoint]
  Services/LocationPermission.swift  the thing that unlocks network names
  Views/MainView.swift         window contents, the 5 s scan loop, status line
  Views/SignalGraph.swift      all the drawing - axes, grid, curves, labels
```

## There is no Xcode project on purpose

SwiftPM cannot produce an app bundle, and that is the only thing Xcode would add.
The `Makefile` copies the binary, `Info.plist` and `.icns` into
`R WiFi Analyzer.app/Contents` and codesigns it. If you add a resource, add it to the
`bundle` target too - nothing else will notice it is missing until runtime.

**It has to run as a bundle.** Location authorization is granted to a bundle
identifier, so running `.build/release/WifiAnalyzer` directly gets a binary that
can never see a network name.

## CoreWLAN, and what it withholds

`CWNetwork` redacts exactly four properties - `ssid`, `ssidData`, `bssid` and
`countryCode` - unless the app is authorized for Location Services. `wlanChannel`,
`rssiValue` and `noiseMeasurement` are always readable. That split is the whole
reason the app is usable without the permission: the graph is correct, only the
labels are `(hidden)`.

Consequences that are load-bearing in the code:

1. **`AccessPoint.id` cannot be the BSSID.** It is `bssid ?? "ssid@channel"`, and
   it is what both deduplication and colour assignment key off. A BSSID that is nil
   for every network would otherwise collapse the whole scan into one entry.
2. **`LocationPermission` must outlive the request.** CLLocationManager delivers
   authorization changes to its delegate; a manager created in a function and
   dropped never reports back. It is stored on `ScanModel` for that reason, and
   granting access triggers an immediate rescan so names appear at once instead of
   up to 5 seconds later. The type does exactly two things - ask, and report the
   answer. There is no `startUpdatingLocation` and no delegate method that receives
   coordinates, deliberately: keep it that way. The *explanation* belongs in
   README.md, not in the window; the system prompt is the only thing a user should
   have to read to decide.
3. **The app must be a GUI app with a running run loop.** Apple's own guidance on
   the "scan returns empty SSIDs" reports is that a command line tool - which only
   spins its run loop while awaiting authorization - gets empty results where a
   windowed app does not. `App.swift` sets `.regular` activation policy for the
   same family of reasons: nothing has told AppKit this hand-assembled bundle is a
   foreground app.

`scanForNetworks(withSSID:includeHidden:)` **blocks** for on the order of a second
while the radio sweeps channels, so it runs on `Task.detached`. That is also why
`WifiScanner` is a stateless enum returning a `ScanResult` value: nothing that
CoreWLAN owns crosses the thread boundary, so no `@unchecked Sendable` is needed
anywhere.

A refused scan is not an error. The driver rate-limits scans, and
`interface.cachedScanResults()` still holds the last sweep - at worst a few seconds
stale. Treating a refusal as failure would blank the graph every other refresh.

## Swift 5 language mode

`Package.swift` uses swift-tools-version 5.9, which means Swift 5 language mode.
Under Swift 6's strict concurrency the CoreWLAN types would each need a Sendable
story they do not have, for no benefit: the concurrency here is one detached task
returning a struct of value types. If you raise the tools version, expect to spend
the afternoon on `CWNetwork`.

## Drawing decisions

Inherited from the phone port unless noted:

- **A `Canvas`, not a stack of Shapes.** Labels have to be measured to be placed,
  and `GraphicsContext.resolve(_:).measure(in:)` is the cheap way to do it. The
  whole canvas is rebuilt per scan rather than diffed; at a few dozen networks that
  is free.
- **The 2.4 GHz axis is fixed at 2400-2500 MHz**; 5 and 6 GHz are fitted to the
  networks present and widened to a **200 MHz minimum** (the phone uses 140, for a
  360 px wide screen). The axis moves when the set of channels in range changes.
- **Curves are painted strongest-first**, so a weak narrow curve lands on top of a
  strong wide one instead of disappearing under it.
- **Labels de-collide upward.** New on this port: a desktop window shows every
  network at once, and a dozen names drawn at their own peak height overlap into a
  smear. Each label is nudged up by its own height until it clears the ones already
  placed, up to six steps. Because labels are placed strongest-first, the strongest
  network keeps the spot it wants.
- **Colours come from an FNV-1a hash of `AccessPoint.id`**, not `Hasher`. Swift's
  hash is seeded per process, so the same network would change colour on every
  launch.
- **The plot follows the system appearance.** The grid, axis text and plot
  background come from `colorScheme`; the 12 curve colours do not, because they
  have to stay distinguishable from each other more than from the background.

## Channel width, and why the beacon has to be parsed for it

`CWChannel.channelWidth` gives 20/40/80/160 MHz, but there is no property for the
*centre* of a wide channel - only `channelNumber`, which is the primary. A 40 MHz
BSS occupies its primary plus one extension channel on one side, so a 42 MHz curve
centred on the primary would claim 20 MHz of spectrum that is actually free.

`WifiScanner.geometry(of:primaryMhz:reportedWidth:)` therefore walks
`CWNetwork.informationElementData` - which needs no permission, unlike the SSID -
for the two elements that state the centre outright:

- **HT Operation (61).** Bit 2 of the second octet is the STA channel width, bits
  0-1 the secondary channel offset: 1 means the extension is above the primary,
  3 below. Both have to agree before it is 40 MHz; a 20 MHz-only BSS on a
  40 MHz-capable radio still sends the element.
- **VHT Operation (192).** Names its centre directly, as a channel number in the
  5 GHz plan.

When the reported width is over 20 MHz and neither element resolves a centre, the
curve **falls back to 22 MHz on the primary** rather than guessing. That is the case
for 6 GHz, whose centre lives in the HE Operation element (255/ext 36) that this
does not parse - so a 6 GHz BSS is drawn at its primary channel only. Adding it is
the obvious next improvement; it needs a 6E AP to verify against.

The width is never written into the label. The width of the curve *is* the display.

## Deliberate omissions

- **No connect / disconnect.** `associateToNetwork` exists; this is a measurement
  tool and joining networks is what the menu bar is for.
- **No history or logging to disk.**
- **No `AccessPoint.security` in the UI.** It is parsed and carried because the
  other two ports carry it, and it is one line; nothing displays it yet.

## The README screenshot

`docs/screenshot.png` is not a picture of anyone's neighbourhood: it was taken from
a build whose `WifiScanner.scan()` was temporarily replaced with a fixed list of
made-up networks, so no real SSID or BSSID appears in it. If you retake it, do the
same - patch, build, capture, revert - rather than blurring a real scan.

## Verification status

- Builds clean (no errors, no warnings) with Swift 6.3.2 on macOS 26.5.2, arm64.
- Run on that machine against live networks: 20 found on `en0`, SSIDs visible (so
  Location access was in effect), the 5 GHz graph correct from channel 36 to 165
  with 80 MHz widths in the labels.
- **Not verified:** 6 GHz, since no 6E AP was in range; the universal
  (`ARCHS="arm64 x86_64"`) build; `make install`; and the first-run Location prompt
  on a machine that has never authorized the app.
